Plugin gratuito para Claude Code

A documentação decide. O código executa.

Living Brain é um método para escrever a documentação antes do código e conferir cada página nova com o que o produto já decidiu. Na prática, você pede em linguagem natural e o Claude Code registra no lugar certo, no formato certo.

Ele lê só o que importa para o pedido

Escolha um pedido. O Living Brain descobre a que área ele pertence, lê os documentos que essa área exige e escreve uma ficha nova. O resto do acervo nem é aberto.

Escolha um pedido.

Negócio

Produto

Técnico

O que cada área lê vem do registro de domínios do plugin. Os nomes das fichas são de um produto fictício.

O problema

O conhecimento de um produto costuma morar em lugares que ninguém consulta na hora certa.

Espalhado

Regras de negócio ficam em tickets, conversas e na cabeça de quem estava na reunião. Quem chega depois não acha, e quem sai leva junto.

Escrito depois

A documentação descreve o que foi construído, não por que foi construído assim. No dia seguinte, ela já está desatualizada.

IA no escuro

Um agente de IA ou recebe o repositório inteiro, e gasta muito, ou não recebe nada, e preenche as lacunas com suposições.

Living Brain trata a documentação como a fonte da verdade do produto. Se a documentação e o código discordam, quem é ajustado é o código.

Como funciona

A documentação fica no seu repositório, em duas camadas com papéis diferentes.

Para pessoas

wiki/

Texto corrido, com contexto e o porquê de cada decisão. É a fonte da verdade, e toda mudança começa aqui.

Para a IA

llm-wiki/

Fichas curtas e independentes, cada uma com um prefixo que diz o que ela é: BR- regra de negócio, FEAT- funcionalidade, ADR- decisão de arquitetura. A IA consulta uma ficha por vez, em vez de ler tudo.

As camadas se organizam em áreas: business/ (negócio), product/ (produto), technical/ (técnico) e um glossário único. A cada pedido, o Living Brain segue sempre o mesmo caminho:

  1. Identifica a área. Descobre se o pedido é de negócio, produto, arquitetura, dados, API, tela, segurança, infraestrutura ou requisito não funcional. Se for ambíguo, pergunta. Se misturar áreas, divide.

  2. Lê o que já foi decidido. Antes de escrever, lê os documentos que aquela área exige. É isso que impede uma página nova de contradizer uma antiga.

  3. Escreve no modelo certo. Aplica o modelo daquele tipo de ficha e as regras da área. Se o pedido contradiz uma regra já registrada, ele aponta a contradição em vez de escrever.

  4. Registra e sincroniza. Anota a mudança no histórico da área e atualiza a camada da IA.

O que ele perguntou em vez de inventar

  1. As 24 horas contam a partir do pedido ou da confirmação do pagamento?
  2. Um cancelamento exatamente às 24h00 ainda vale?
  3. Dentro das 24 horas, algum status (como "enviado") impede o cliente de cancelar?
  4. Depois das 24 horas, o que o cliente vê, e ele pode pedir a um administrador?
  5. Como um pedido é identificado, por exemplo, por um número?

Tudo o que ele escreveu ficou marcado como rascunho até alguém revisar. As perguntas ficaram registradas na própria documentação, para serem respondidas depois.

Como ele se diferencia

Living Brain não substitui Scrum, Shape Up, TDD ou DDD. Cada área continua usando as boas práticas do seu campo. O que muda é quem decide o que é verdade.

E as ferramentas de IA que escrevem código?

Copilot, Cursor e afins trabalham no nível do código, dentro de uma conversa. Living Brain trabalha uma camada acima, e os dois se complementam: ele dá a essas ferramentas um contexto organizado para consultar.

O que ele não faz

Dito com a mesma clareza, porque a diferença importa.

Não bloqueia commit

Documentar antes de codar é uma disciplina que o time assume. Nenhum hook ou CI impede um commit sem documentação.

Não promete números

Ler fichas pequenas carrega menos contexto do que ler documentos inteiros. Quanto se economiza ainda não foi medido.

Não roda fora do Claude Code

É um plugin do Claude Code. O chat comum do Claude não carrega plugins.

Não é rápido no começo

Escrever antes custa tempo no início. O retorno vem com menos retrabalho e um produto que se explica sozinho.

Instalar

Funciona só no Claude Code: no terminal, no app desktop do Claude Code, nas extensões de IDE (VS Code, JetBrains) ou em claude.ai/code.

Não funciona no chat comum do claude.ai, nos apps de chat do Claude para desktop e celular, nem em Projetos. Se o comando /plugin não existe onde você digita, você está no chat, e não no Claude Code.

  1. Abra o Claude Code na pasta do seu projeto. Pode ser um repositório só de documentação.

  2. Adicione o marketplace do Living Brain.

    /plugin marketplace add davidcromianski-dev/living-brain

  3. Instale o plugin.

    /plugin install living-brain@living-brain

  4. Recarregue os plugins.

    /reload-plugins

  5. Confira. Rode /plugin e veja se o living-brain aparece habilitado. Pronto: é só pedir.

Instalar para o time inteiro, de uma vez

Crie ou edite o arquivo .claude/settings.json na raiz do projeto e faça commit dele. Quem clonar o projeto recebe o plugin ao abrir o Claude Code e aceitar a confiança no projeto.

{
  "extraKnownMarketplaces": {
    "living-brain": {
      "source": {
        "source": "github",
        "repo": "davidcromianski-dev/living-brain",
        "ref": "v0.1.1"
      }
    }
  },
  "enabledPlugins": {
    "living-brain@living-brain": true
  }
}

O ref fixa a versão, para todo o time usar a mesma. As versões publicadas estão nas tags do repositório.

Onde os documentos ficam

Por padrão, na raiz do projeto: business/, product/, technical/ e glossary/. Você não precisa criar nada antes. As pastas aparecem no primeiro pedido.

Se preferir guardar tudo numa pasta, crie o arquivo .living-brain.yml na raiz com esta linha:

docs-root: docs/
Atualizar para uma versão nova
/plugin marketplace update living-brain

Depois, rode /reload-plugins. Se você fixou a versão no settings.json, troque o ref pela tag nova.

Exemplos de pedidos

Fale como falaria com uma pessoa do time. Você não escolhe especialista nem modelo: o Living Brain descobre a área sozinho.

Negócio

  • Documente esta regra de negócio: um pedido só pode ser cancelado pelo cliente em até 24 horas após a compra. Depois disso, só um administrador pode cancelar.
  • Registre os atores do módulo de pagamentos: cliente, atendente e financeiro, com o que cada um pode fazer.
  • Adicione ao glossário o termo "pedido faturado" e explique o que o diferencia de "pedido pago".

Produto

  • Adicione uma feature com histórias de usuário e critérios de aceite para o onboarding de novos pacientes.
  • Registre a decisão de produto: não teremos app mobile na primeira versão. Inclua o porquê e as alternativas descartadas.
  • Crie a persona do gestor de clínica que aprova agendamentos.

Revisão

  • Verifique se a documentação técnica está coerente com as regras de negócio e aponte as divergências.

Técnico

  • Registre uma decisão de arquitetura: escolhemos um monólito modular em vez de microsserviços, porque o time é pequeno.
  • Defina o requisito não funcional de latência: 95% das chamadas da API devem responder em menos de 300 ms.
  • Documente o modelo de dados da tabela de pedidos: colunas, tipos, chaves e índices.
  • Documente o endpoint de cancelamento de pedido, com requisição, resposta e erros possíveis.
  • Especifique a página de lista de pedidos: rota, estados de vazio, carregando e erro, e quais endpoints ela consome.
  • Documente a autenticação: login com OAuth2 e segundo fator obrigatório para administradores.
  • Descreva o pipeline de CI/CD e os ambientes de desenvolvimento, homologação e produção.

Dicas

  • Seja específico na regra e deixe o formato com ele. Você diz o quê, ele cuida de onde e como.
  • Um pedido que mistura áreas, como uma regra que também exige uma tabela nova, é dividido em partes, uma por área.
  • Se faltar informação, ele registra a dúvida em vez de supor. Responda depois com "as 24 horas contam a partir do pagamento", por exemplo, e ele atualiza.
  • Revise o que ele escreveu. O conteúdo novo fica marcado como rascunho até uma pessoa conferir.

Perguntas frequentes

Funciona no chat do Claude, no app do celular ou num Projeto?

Não. Living Brain é um plugin do Claude Code, e só o Claude Code carrega plugins. Funciona no terminal, no app desktop do Claude Code, nas extensões de IDE e em claude.ai/code.

Preciso saber programar?

Não para usar. Você precisa abrir o Claude Code numa pasta e digitar os dois comandos de instalação. Depois disso, os pedidos são em linguagem natural.

Em que idioma os documentos são escritos?

Você pode conversar em português, mas hoje o plugin escreve os arquivos em inglês. É uma regra atual do método, pensada para manter a documentação consistente.

Onde ficam os documentos? O Living Brain guarda alguma coisa?

Tudo fica no seu próprio repositório. O Living Brain não guarda, não copia e não envia nada do seu produto para lugar nenhum. Ele só traz o método e os modelos.

Já tenho uma pasta de documentação. Ele bagunça a estrutura?

Você pode apontar onde a documentação fica com o arquivo .living-brain.yml, usando docs-root. Também é possível indicar que um documento específico mora em outro lugar, ou que ele não existe no seu projeto.

Ele impede alguém de subir código sem documentação?

Não. Documentar antes é uma disciplina do time. O que ele garante é que cada documento novo seja conferido com o que já está registrado.

Quanto custa?

O plugin é gratuito e de código aberto, sob a licença MIT. O uso do Claude Code segue o seu plano do Claude.

O que os números de clones no topo da página contam?

Quando alguém adiciona o marketplace do Living Brain, o Claude Code clona este repositório, e o GitHub registra esse clone. Por isso o número de clones é o sinal público mais próximo de uma instalação. Mas ele não é uma contagem de instalações: também entram atualizações do plugin, clones de quem só quis ler o código, automações e as sessões do próprio autor. "Origens diferentes" é a contagem de clonadores únicos que o GitHub faz numa janela de 14 dias.

O GitHub só guarda esses dados por 14 dias, então uma automação salva os números uma vez por dia. Os dados brutos são públicos, no arquivo traffic.json.

Preciso instalar mais alguma coisa?

Não. Opcionalmente, o plugin superpowers permite que ele delegue documentos longos a subagentes, para não lotar a conversa principal. O Living Brain funciona sem ele.

Ficou com alguma dúvida?

Abra uma dúvida no GitHub. A resposta fica pública e ajuda quem tiver a mesma pergunta depois.

Sugestões e relatos de uso também são muito bem-vindos, inclusive de quem testou e achou que não serve para o seu caso.
